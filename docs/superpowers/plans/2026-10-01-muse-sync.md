# Muse Sync Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Muse posts application batches to a relay in this Vercel project. Paceboard pulls them, auto-applies clean items, sends ambiguous ones to Review, and publishes a compact ledger back for Muse.

**Architecture:** Web-standard Vercel Functions in `api/` sit in front of Upstash Redis (a stream for batches, a key for the ledger) behind two bearer keys. A dependency-free wire contract in `shared/` is used by both the relay and the app. In the browser, a pure planner (`planMuseIngest`) decides what each item does. The repository commits items, entry writes, and the cursor atomically. A hook drives pulling, polling, ledger publishing, review, and undo.

**Tech stack:** React 19, Dexie 4, Vitest 3 (jsdom; node environment for relay tests), Vercel Functions (Node, Web Request/Response), `@upstash/redis`.

**Design:** `docs/superpowers/specs/2026-10-01-muse-sync-design.md`

**Conventions:**
- Code under `api/` and `shared/` imports relative files **with `.js` extensions** so Vercel's Node ESM runtime resolves them whether or not it bundles. `shared/` has no runtime imports from `src/`.
- There is no `@types/node`. The relay uses only Web APIs (`Request`, `Response`, `crypto.subtle`, `TextEncoder`) and reads env through `globalThis.process?.env`.
- Run a single file with `npx vitest run <path>` and everything with `npm test`. Lint with `npm run lint`; type-check and build with `npm run build`.

### Task 2: Relay store and handlers

**Files:** create `api/_lib/store.ts` (the `RelayStore` interface and `createMemoryStore`), `api/_lib/upstashStore.ts`, `api/_lib/auth.ts`, `api/_lib/handlers.ts`, `api/muse/batches.ts`, `api/muse/ledger.ts`, and `api/_lib/handlers.test.ts` (`// @vitest-environment node`). Create `tsconfig.api.json` and add its reference in `tsconfig.json`. Add `@upstash/redis` to dependencies.

`RelayStore`:
```ts
interface StoredBatch { id: string; receivedAt: string; batch: MuseBatch }
interface RelayStore {
  appendBatch(batch: MuseBatch, receivedAt: string, retentionMs: number): Promise<{ id: string; duplicate: boolean }>
  readBatches(after: string | null, limit: number): Promise<{ batches: StoredBatch[]; hasMore: boolean; oldestId: string | null }>
  getLedger(): Promise<MuseLedger | null>
  putLedger(ledger: MuseLedger): Promise<void>
}
```
- **Memory store:** monotonic `"<ms>-<seq>"` IDs, a `batchId` map, retention trimming, and stream-ID comparison by `[ms, seq]`.
- **Upstash store:**
  - `xadd('muse:batches', '*', { batchId, receivedAt, batch: JSON }, { trim: { type: 'MINID', threshold: <ms>-0, comparison: '~' } })`, then `set('muse:batch:<id>', streamId, { nx: true, ex: 90d })`. If the NX set fails, `xdel` the new entry and return the existing ID with `duplicate: true`.
  - Reads use `xrange(key, start, '+', limit + 1)`, with `start` set to the successor of `after` (`ms-(seq+1)`). The oldest ID comes from `xrange(key, '-', '+', 1)`.
  - Values may come back already deserialized, so parse only when the value is a string.
- **Handlers:** `handleBatches(request, deps)` and `handleLedger(request, deps)` with `deps = { env, store: () => RelayStore | null, now: () => Date }`.

Tests (memory store):
1. Auth:
   - no or incorrect key → 401
   - the Muse key cannot GET batches, and the Paceboard key cannot POST batches
   - missing env keys → 503
   - a missing store → 503
2. POST:
   - invalid JSON → 400
   - schema issues → 400 with `issues`
   - more than 256 KB → 413
   - valid → 201 `{ id, duplicate: false }`
   - the same `batchId` again → 200 `{ id: same, duplicate: true }`
3. GET:
   - paging with `limit` and `after`; `hasMore` and `nextCursor`; `oldestId`
   - an empty stream → `{ batches: [], nextCursor: null }`
4. Ledger:
   - PUT with the Paceboard key, then GET with the Muse key round-trips
   - GET before any PUT → 404
   - PUT with the wrong schema → 400
5. Unsupported method → 405 with an `Allow` header.

The function files are thin:
```ts
import { handleBatches, defaultDeps } from '../_lib/handlers.js'
export default { fetch: (request: Request) => handleBatches(request, defaultDeps()) }
```
Run the tests and commit `feat: add Muse relay functions`.

### Task 3: Ingest planner (`src/domain/muse.ts`)

**Files:** create `src/domain/muse.ts` and `src/domain/muse.test.ts`. Modify `src/domain/types.ts` (Muse types) and `src/domain/status.ts` (`appendStatus` accepts an optional event `id`).

Types:
- `MuseItemState = 'applied' | 'pending' | 'dismissed' | 'skipped'`
- `MuseReviewReason = 'invalid' | 'possible_duplicate' | 'unmatched' | 'low_confidence' | 'closed_application' | 'undone'`
- `MuseItem`, as in the spec
- `MuseSyncState { key: 'muse'; cursor?; lastPulledAt?; lastLedgerHash?; lastLedgerPublishedAt?; retentionGap? }`
- `MuseData { items: MuseItem[]; syncState: MuseSyncState }`

`planMuseIngest({ batches, entries, knownKeys, gmailCandidates, receivedAt })` returns `{ items, entryWrites, gmailResolutions, summary: { created, filled, statuses, review, skipped } }`. It walks items in order against a working copy of the entries, following the spec's rules exactly.

Tests:
1. A clean new entry → applied/created, using Muse's ID, with an `applied` history event on `submittedDate`.
2. An existing ID → skipped; an existing `knownKeys` key → no item at all.
3. A Gmail origin on an existing entry → filled. Only blank fields are filled, and `filledFields` is recorded. Nothing blank → skipped.
4. A fuzzy duplicate → pending/possible_duplicate with `suggestedEntryIds`.
5. Invalid entry data → pending/invalid with `detail`.
6. Status by `entryId` → applied/status_added, with event `id` = payload `id` and the origin kept.
7. Status by exact `match` → applied. An ambiguous or missing match → pending/unmatched with suggestions.
8. Low confidence → pending. A target that is rejected → pending/closed_application. The same status as current → skipped. A date before submission → pending/invalid.
9. A duplicate event ID or Gmail message ID → skipped.
10. An entry plus its status in the same batch → both applied.
11. A pending Gmail candidate with a matching message ID → in `gmailResolutions`, imported, with `linkedEntryId`.
12. Re-planning the same batches with the previous output's keys → nothing new.

Also implement and test:
- `fillBlankFields(entry, payload)`
- `undoMuseItem(item, entries)` → `{ write?: ApplicationEntry; deleteId?: string }`, covering created, status_added, and filled (clearing only fields that still hold Muse's values)
- `buildLedger(entries, settings, syncState, pendingCount, generatedAt)`
- `ledgerHash(ledger)`, which ignores `generatedAt`

Commit `feat: plan Muse batch ingest`.

### Task 6: `useMuseSync` hook

**Files:** create `src/hooks/useMuseSync.ts`.

The controller exposes:
- state: `connected`, `status` (`idle | syncing | error`), `error`, `errorCode`, `data` (`MuseData`), `pendingItems`, `appliedItems`, `dismissedItems`, `lastResult`
- connection: `connect(key)`, `disconnect()`, `pullNow()`
- review: `resolveEntry(item, { mode: 'fill' | 'create', entryId? })`, `applyStatus(item, entryId)`, `dismiss(item)`, `restore(item)`, `undo(item)`
- `clearLastResult()`

Behavior:
- Pull triggers: on mount when a key exists, on `visibilitychange` to visible (throttled to once a minute), and on an interval (default 10 minutes, injectable).
- A 401 clears the stored key and sets the "The sync key was rejected." error. A 503 keeps the key.
- Ledger publishing runs on a debounced effect over `entries`, `settings`, and Muse data, and publishes only when the hash changed.

The hook is covered through App tests in Task 8. Commit with Task 7.
